# H. RAG 知识库设计（V1.0）

## 当前结论

第一版采用“结构化 JSON 知识源 + 本地关键词/中文双字检索 + 证据引用”的简化 RAG，不接向量数据库，也不调用真实模型。先验证用户是否真的会问插画垂类问题、能否召回正确证据，以及无答案时能否拒答；知识量或同义表达增长后再评估 Embedding 和 Rerank。

RAG 只负责行业术语、黑话、平台规则说明和参考案例。实时画加/小红书数据、热点分、Opportunity Score、用户画像、权限和业务红线仍由结构化数据、规则与 Validator 负责。

## 知识资产

| 文件 | 内容 | 当前权威状态 |
|---|---|---|
| `source_registry.json` | 来源、URL、权威性、状态和用途 | 已建立 |
| `industry_terms.json` | OC、兽设、买断、排单、水彩等候选术语 | 待用户逐条确认 |
| `platform_rules.json` | 画加与小红书官方页面范围内规则 | 官方来源；严格限制适用范围 |
| `reference_cases.json` | 用户授权的作品能力案例 | 作品事实有效，经营效果待验证 |
| `index/chunks.json` | 可重建的检索索引 | 由脚本生成，不是权威源 |

“优秀案例”暂未建立。现有作品没有曝光、咨询、成交、复购或对照数据，只能称为参考案例，不能宣称营销成功。

## 离线链路

`来源登记 → 权威/授权/状态检查 → 结构化知识记录 → 一条知识一个 Chunk → 关键词与中文双字索引 → 测试 → 发布索引`

知识源更新后运行：

```bash
source .venv/bin/activate
python scripts/build_knowledge_index.py
```

源文件是事实库，`index/chunks.json` 只是派生物；索引错误或过期时可重新生成。

## 在线链路

`用户问题 → 非空与长度校验 → 类型/平台过滤 → 稀疏检索 → 权威性辅助排序 → 最低相关度判断 → Evidence Package → Prompt/LLM（后续）→ Schema/引用校验 → 回答或 no_answer`

`/rag/search` 只返回证据，用于单独检验“有没有找到正确知识”。`/rag/answer` 当前采用保守的抽取式回答：返回最高相关证据并附引用，候选知识自动提示待确认；后续接入 LLM 时仍必须通过相同 Schema 和引用白名单校验。

## 状态和边界

- `ready`：检索到超过最低相关度的证据。
- `no_answer`：未找到足够证据，不能用常识补齐。
- `need_input`：问题为空。
- `candidate_needs_user_confirmation`：可用于候选回答，但必须告诉用户口径待确认。
- `needs_manual_review`：只登记了官方页面，尚未核对可引用的具体条文。
- `active_for_stated_scope`：仅对记录中的 scope 有效，不可外推。

## 用户需要提供的行业知识

每条知识建议提供：术语、别名、你认可的定义、常见误解、适用业务、反例和是否允许进入 Demo。平台经验必须区分“个人经验”与“平台正式规则”。

要把作品案例升级为优秀案例，还需要：发布平台、发布时间、内容形式、曝光、点赞/收藏/评论、主页访问、咨询、成交、复购、投入时间，以及你认为有效的原因和反向因素。

## 验收

至少覆盖：术语直问、别名、媒介歧义、平台规则范围、参考案例、无答案、Prompt 注入和过期规则。当前单元测试验证买断、水彩、平台授权范围、未知问题拒答及案例不夸大。

> 本流程只作信息结构参考。项目负责人需要能够独立解释每个知识来源、状态、检索结果和失败分支。
